## 3. Flags per CLI (verified)

### Claude Code

```
claude -p --model <alias> --effort <low|medium|high|xhigh|max>
  --system-prompt "<text>"            # or --append-system-prompt
  --tools "" --strict-mcp-config --disable-slash-commands
  --setting-sources "" --no-session-persistence --permission-prompts none
  --output-format json | stream-json [--verbose --include-partial-messages]
  [--json-schema '<schema>']
```

- Prompt: argument or **stdin** (verified).
- `--tools ""` alone leaves MCP servers from claude.ai connectors active (8 tools seen). Adding `--strict-mcp-config` (with no `--mcp-config`) gives `tools: []`, `mcp_servers: []`, `slash_commands: []` (fixture `stream-json-locked.jsonl`).
- Model aliases: `sonnet, opus, haiku, fable, best, sonnet[1m], opus[1m], fable[1m], opusplan, default`, or a full model ID. Obtained by sending `/model` as the prompt in `-p` mode, which **works headless** (fixture `slash-model.json`) → dynamic discovery is possible for Claude. Re-captured 2026-09-22 unchanged, and the fixture is now read by `test/config.test.ts`, which checks every Claude `cli_model` against it. The three `[1m]` aliases are exposed as models of their own; `best`, `default` and `opusplan` are not, being routing aliases onto models the table already names.
- Effort: `claude --help` gives `--effort <level>` as `low, medium, high, xhigh, max` (2026-09-22). Five levels, not the three the gateway priced until that date.
- `json` output: single object with `result`, `is_error`, `subtype`, `usage.{input_tokens,output_tokens,cache_*}`, `total_cost_usd` (notional on a subscription), `session_id`.
- `stream-json` output: `system/init`, `stream_event` (Anthropic API events, `content_block_delta` carries text), `assistant`, `rate_limit_event`, final `result`.
- **`rate_limit_event`** exposes the real subscription windows: `unifiedWindows.five_hour.{utilization,resetsAt}` and `seven_day.{utilization,resetsAt}`. The gateway can read real limits instead of estimating.
- Images: with `--tools ""` Claude cannot read files. Phase 2 option: `--tools Read --restricted` (file tools confined to the working directory) or `--input-format stream-json` with image content blocks. Not needed in phase 1.
- Latency for a one-word answer: ~1.7 s.

### Codex

```
codex exec --json --ephemeral --skip-git-repo-check --ignore-user-config
  -C <sandbox dir> -s read-only
  -c 'features.shell_tool=false' -c 'web_search="disabled"'
  -c 'model_reasoning_effort="<minimal|low|medium|high|xhigh>"'
  -c 'developer_instructions="<system prompt>"'
  [-m <model>] [-i <image>...] [--output-schema <file>] -
```

- Prompt: argument, or stdin with `-` (docs). **Stdin must be closed or used**: when stdin is not a TTY Codex reads it ("Reading additional input from stdin..."), so the runner must either write the prompt to stdin or pass `</dev/null`.
- `developer_instructions` works as system prompt (verified: "Always answer in uppercase" → `OK`).
- Output JSONL events: `thread.started`, `turn.started`, `item.completed` with `item.type == "agent_message"` and `item.text`, `turn.completed` with `usage.{input_tokens,cached_input_tokens,output_tokens,reasoning_output_tokens}`; also `turn.failed`, `error` (docs). No token deltas: the answer arrives whole in `item.completed`.
- No model list command, but the CLI keeps a **model cache** that is one: `$CODEX_HOME/models_cache.json` carries, per model, the slug, the display name, the default reasoning level and the levels it serves. Dumped on the host 2026-09-22 (client 0.155.1) and committed as `test/fixtures/codex/models.txt`, which `test/config.test.ts` now checks every `cli_model` and every declared effort against. Nine slugs: `gpt-6-astra`, `gpt-6-sol`, `gpt-6-luna`, `gpt-reserve`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`, `codex-auto-review`. The levels are **per model**, not per CLI — `gpt-5.5` stops at `xhigh`, four of the nine reach `ultra` — which is why each entry that serves fewer than the whole table pins its own `efforts`. The `minimal` this section once listed is not in the cache and no model offers it; the levels are `low, medium, high, xhigh, max, ultra`.
- Latency: ~7.5 s for a one-word answer (startup dominated).

### Antigravity (`agy`)

```
agy -p '<prompt>' --model <id> --output-format json | stream-json
  --disable-slash-commands --print-timeout <dur> [--json-schema <schema>]
# or, prompt via stdin:
agy -p= --input-format stream-json --output-format stream-json --model <id> ...
  <<< '{"event":"user","message":{"role":"user","content":"<prompt>"}}'
```

- `-p` takes the prompt as its value; `-p -` sends a literal dash. Stdin works only with `--input-format stream-json` and the `user` event above (verified; the format is undocumented, found via the CLI's own error messages).
- `agy models` lists models: `gemini-3.8-flash-{high,medium,low}`, `gemini-3.7-flash-*`, `gemini-3.6-flash-*`, `gemini-3.1-pro-{high,low}`, `claude-sonnet-4-6`, `claude-opus-4-6-thinking`, `gpt-oss-120b-medium`. Effort is part of the model id; a separate `--effort` flag also exists.
- `json` output: `{status: "SUCCESS"|"ERROR", response, error?, usage.{input_tokens,output_tokens,thinking_tokens,cache_read_tokens,total_tokens}}`. `stream-json`: `init`, `step_update` with `text_delta`, final `result`.
- **Tools cannot be disabled by flag.** `init` lists 57 tools (`run_command`, `write_to_file`, browser, `search_web`, …) even with `--sandbox --mode plan`. Permission model is in `~/.gemini/antigravity-cli/settings.json`: `toolPermission` ∈ `request-review` (default), `proceed-in-sandbox`, `always-proceed`, `strict`; `permissions.{allow,deny}` with `command(...)` entries; `allowNonWorkspaceAccess`; `enableTerminalSandbox`. In `-p` mode a tool call that needs approval **stalls forever and `--print-timeout` does not fire** ([issue #548](https://github.com/google-antigravity/antigravity-cli/issues/548)).
- Consequence for the runner: the `runner` user gets its own `settings.json` with `toolPermission: "strict"`, `enableTerminalSandbox: true`, `allowNonWorkspaceAccess: false`, and the runner enforces its own hard timeout with SIGKILL. A prompt injection that tries to run a command stalls until killed instead of executing. Whether `permissions.deny` works headless is untested; verify in the LXC.
- `agy` injects personal context from its state directory (it greeted the owner by name in one test). The `runner` user's state starts empty, so this does not apply in the LXC, but it is a reason never to run the gateway under a personal account.
- Latency: ~3.8 s for a one-word answer.

## 7. Reference: 0xDarkMatter/conclave (read 2026-09-20)

Go, MIT, a terminal tool that wraps the same CLIs plus Grok, Perplexity and
direct APIs. What we take and what we do differently:

- **Codex prompt on stdin, never as an argument.** Their comment records two
  real failures: Windows shims cut arguments at the first newline, and the 32K
  command-line limit. We already use stdin for all three CLIs.
- **Per-provider timeouts, not a global one** (ADR-003): a hung provider
  cannot block the others, and the judge synthesizes partial results. Same as
  our §7.1 and phase 2 sketch.
- **Preflight** (`preflight.go`): each provider gets an auth check at startup
  with a 5 s budget, because a decorated provider silently losing its check
  showed up as "a mysterious 401 mid-query". Same intent as our `health()`;
  our check also marks the model unavailable in `/v1/models`.
- **Provider decorators** (model override, response cache) wrap a base
  provider. A response cache keyed on the full prompt (ADR-011) is a cheap
  idea for repeated council runs; not in phase 1.
- **Their CLI invocations disable nothing**: Claude runs as `--print <prompt>
  --model <m> --output-format json` with all tools, Codex `exec -m <m>
  --skip-git-repo-check` with its default sandbox. Fine for a developer's own
  terminal, not for a process that receives prompts from the internet. Our
  runner is stricter by necessity (§8.4 of the spec).
- **Grok, Perplexity, GLM, OpenRouter**: each needs its own subscription or
  API key. Not adopted. Council members in Capitoline are (provider, model)
  pairs, so diversity comes from the existing subscriptions first.
- Their Gemini adapter targets the old `gemini` CLI, not `agy`; nothing to
  reuse there.

## 8. Antigravity image generation (2026-09-21)

`agy`'s agent has a `generate_image` tool (internal model `gemini-3.1-flash-image`).
Findings on the deployed host, with the runner's `strict` settings:

- **It runs headless under `strict`.** No `--dangerously-skip-permissions` is
  needed: for `agy` an image generation is not a file write, so it does not ask
  for approval, while `run_command` and file writes still stall. The tool takes
  only `ImageName` and `Prompt`; there is no size parameter.
- **The image never reaches the working directory.** It is written to
  `$HOME/.gemini/antigravity-cli/brain/<conversation_id>/image_<ts>.jpg` (JPEG,
  1376x768 for a 16:9 request, ~1 MB, mode 0644). The agent's claim that it
  saved `./image.png` is invented. `scripts/capitoline-collect-image` reads it
  out through `sudo` and removes the conversation directory.
- **Stream events**: `step_update` with `"step_type":"tool"`, states `ACTIVE` →
  `DONE` (or `ERROR`), carrying `tool_name` and `tool_info.parameters`.

### Two quotas, both rolling windows

| Window | Cap | Evidence |
|---|---|---|
| 5 hours from the first generation | 12 | measured 2026-09-19/20 |
| 7 days from the first generation | 58 | 51 generations on the owner's Mac (verified distinct by md5) plus 7 here, each confirmed by a tool step reaching `DONE`; the 59th attempt was refused with a tool step in `ERROR`. The announced reset, 2026-09-26T18:40:40Z, is 6 d 23 h 59 m 40 s after the first generation of the week (2026-09-19 18:41 UTC) |

58 over 7 days is a little over 8 per day. Both limits apply: a burst of 12 is allowed, but it
spends a seventh of the week.

**One pool, not two.** The owner's runs on the Mac and this spike's runs on the
host both go through `agy` signed in to the same Google AI Pro subscription, so
they share the counter: the owner reached ~51 without a refusal, these 7 pushed
the same window over its cap. A Gemini API key would be a different pool
entirely, and is excluded by the no-pay-per-use rule.

Failed attempts do not seem to consume quota: the refusals themselves, and the
placeholder PNGs written while the short window was closed, are not counted
here.

### The refusal is structured, and the run still says SUCCESS

The tool step arrives with `"state":"ERROR"` and
`tool_info.error.message = "failed to generate content: 429 Too Many Requests, body: {...}"`,
whose embedded JSON carries:

```json
{"error": {"code": 429, "status": "RESOURCE_EXHAUSTED",
  "details": [
    {"reason": "QUOTA_EXHAUSTED", "domain": "cloudcode-pa.googleapis.com",
     "metadata": {"model": "gemini-3.1-flash-image",
       "quotaResetDelay": "122h50m8.592940533s",
       "quotaResetTimeStamp": "2026-09-26T18:40:40Z"}},
    {"retryDelay": "442208.592940533s"}]}}
```

The session then ends `RESULT SUCCESS` with the agent's text: the silent
failure. A reset delay of hours means the short window, of days the long one,
so code must read the returned instant and never assume five hours. Fixtures:
`test/fixtures/antigravity/image-run.jsonl` (success) and `image-429.jsonl`
(refusal), both real.

All of this is implemented: `POST /v1/images/generations` and the MCP tool
`generate_image` (`README.md`), with the helper installed as in
`docs/deploy.md` §7.1.

## 9. How each CLI signals a refusal (real captures, 2026-09-21)

Captured on the host with deliberately invalid credentials, and, for the
Claude quota, with a model that was genuinely exhausted on the subscription.
No quota was spent: a refused request costs nothing.

| CLI | Case | Exit | Where the signal is | What it says |
|---|---|---|---|---|
| Claude | model quota exhausted | 1 | result JSON: `is_error: true`, `terminal_reason: "api_error"`, **`api_error_status: 429`** | "You've reached your Fable limit. Switch to another model, or manage usage credits at claude.ai/settings/usage…" |
| Claude | invalid OAuth token | 1 | same, `api_error_status: 401` | "Failed to authenticate. API Error: 401 OAuth access token is invalid." |
| Codex | invalid credentials | 1 | stdout JSONL `{"type":"error","message":…}`, repeated 5 times, plus stderr | "Reconnecting… 2/5 (unexpected status 401 Unauthorized: Missing bearer or basic authentication in header, url: wss://api.openai.com/v1/responses…)" |
| Antigravity | no credentials | 1 | result JSON `status: "ERROR"`, `error` field | "authentication failed or timed out" (stderr first prints the login URL and waits 60 s) |

Two things worth keeping in mind:

- **`subtype` stays `"success"` on a Claude error**; `is_error` and
  `api_error_status` are the fields that tell the truth.
- **The Claude refusal text matches no rate-limit vocabulary**: "reached your
  Fable limit" contains neither "rate limit" nor "quota" nor "429", so a
  classifier reading the prose calls it a crash. `api_error_status` is the
  only reliable signal, and it is also the one that distinguishes a
  model-specific limit from a subscription-wide one: the same account kept
  answering on other models while Fable was refused.

## 10. Token accounting, settled and unsettled (2026-09-22)

**Antigravity's thinking tokens are inside `output_tokens`.** Proven with a
discriminating prompt rather than by arithmetic: `gemini-3.1-pro-high` asked
for a one-word answer replied `Paris` with `output=203, thinking=202`, so the
output holds the reasoning plus the single word of the answer. Fixture:
`test/fixtures/antigravity/usage-reasoning-oneword.json`. The earlier reading
of a repeated prompt — the CLI's `total_tokens` equals `input + output` — was
not proof of this, because that same total also leaves `cache_read_tokens`
out, so it says nothing about what the two fields contain. `antigravity.ts`
counts `output_tokens` alone and adds `cache_read_tokens` to the input, which
is correct on both counts.

**The three adapters count cached input three ways, and each is right.** A
capture with the same prompt twice through `codex exec` could not settle it
(`input=13399 cached=4480`, then `input=11738 cached=2432`: the input moves
between identical prompts, so neither reading is excluded). What settles it
is each provider's own convention: OpenAI reports cached and reasoning tokens
*inside* the prompt and completion counts, Anthropic reports cached reads
*beside* the input, Antigravity leaves them out of its own total. The
consequence to keep in mind when reading `/health` or the usage table: the
per-provider numbers are not comparable with each other, and no single
formula would make them so.

**Codex's cached input is inside `input_tokens` — measured (2026-09-23).** The
convention above was the documented one and the capture could not confirm
it. What confirms it is a prompt whose input count holds still while its
cache changes. Run on the host as `runner`, outside the gateway so the
working directory was under control, with a prompt of about 3000 tokens
opened by a random nonce so the first run started cold, `gpt-5.5` at `low`:

| Run | Directory | `input_tokens` | `cached_input_tokens` |
|---|---|---|---|
| A | fixed | 16 048 | 6 656 |
| B | fixed | 14 387 | 0 |
| C | other | 14 405 | 6 656 |
| D | fixed | 14 387 | 0 |
| E | other | 14 405 | 8 704 |
| F | fixed | 14 387 | 13 824 |

In the fixed directory the input is 14 387 three times out of three while the
cached count goes 0, 0, 13 824. Had the cached tokens been counted beside the
input, F's prompt would have been reported 13 824 tokens shorter than D's for
an identical request. So `codex.ts` is right to take `input_tokens` as it
comes and add nothing, which is what it does.

Two things came out that the probe was not built for. **The working directory
enters Codex's prompt**, by 18 tokens between the two paths used — so no two
requests through the gateway, each in its own randomly named sandbox, can have
an identical input. And **Codex sometimes adds a block of exactly 1 661
tokens**: run A carried it and B to F did not, and it is also precisely the
difference between the two captures of 2026-09-22 (13 399 and 11 738), which
had been put down to the prompt moving between runs. What the block holds is
not known; it is intermittent, it is not the directory, and it does not affect
the conclusion, which rests on D against F. The cache itself is best-effort —
B and D missed entirely right after a warm run — which is why one pair could
not have settled this and the table has three runs in one directory.

**Antigravity 1.2.8 soft-denies a tool instead of stalling (2026-09-23).** §3
records that in `-p` mode a tool call needing approval stalled for ever and
`--print-timeout` did not fire, which is why the runner's hard SIGKILL exists.
It no longer stalls. Under the runner's `toolPermission: strict` the CLI logs
`Print mode: soft-denying tool confirmation "RunCommand"`, the step ends, and
the run finishes at once — with an **empty response** if the model had meant
to answer after the tool. Checked that the denial is real: asked to `touch` a
marker file in its working directory, the model tried, and the file exists
nowhere under `/tmp` or the runner's home. The sandbox holds; what changed is
that a model which decides to verify something on the machine now answers
nothing instead of hanging. The high-reasoning Gemini models do exactly that
on questions they can check — `sysctl` for keepalive defaults, a test run for
a regular expression — which is the defect recorded in `docs/backlog.md`.

**Sandboxes.** Zero under `/var/lib/capitoline/sandboxes` with the service up
and serving. The eight seen earlier were `spike-*` directories left by the
image spike's own script, not by the gateway.
