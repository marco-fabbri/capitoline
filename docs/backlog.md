## Tests

- **A flaky test in the suite.** Seen twice on 2026-09-22, both times a single failure that passed on the next run with nothing changed; once identified as `POST /v1/images/generations > maps provider error timeout to 504`, once unidentified because the second run was already green. A test that fails at random is worse than a missing one: it teaches the reader to ignore red. Find it by running the suite in a loop with `--reporter=verbose` until it reproduces, and fix the timing assumption rather than widening the timeout — the timeout path is exercised through the fake CLI's `hang` mode and a real deadline, so the race is probably between the runner's kill and the assertion.

## Council

- **The judge can introduce an error none of the members made.** Measured on the first ladder deliberation (2026-09-22, `capitoline-gemini` on a Nutanix RF2 question whose ground truth the owner could verify). The blind peer ranking worked: it put `agy-gemini-flash-high` first unanimously, and that answer was also the only one correct on the contested point, saying "zero redundancy on **affected blocks**" where the others claimed both replicas survive. The judge, `claude-haiku`, then merged the four answers and shipped the wrong claim — "both replicas survive on the two remaining nodes", false for about two thirds of the extents in a three-node RF2 cluster — plus a right conclusion attached to the wrong mechanism. Nothing in the design can catch this: the ranking judges the members' answers, never the synthesis, so an error born in stage 3 is invisible to stages 1 and 2. Three things worth trying, in order of cost: tell the judge in its prompt to prefer the top-ranked answer and to merge only what does not contradict it, rather than blending freely; seat a stronger judge for councils where correctness matters more than price, which is a configuration change; or add a fourth stage where one member checks the synthesis against the answers, which doubles the tail of every deliberation and should not be built before the first two are measured.

## Deployment

- `config/overlay.example.yaml`: `providers.claude.args` is a repository value duplicated in the host's overlay, and so, in the same class, is `providers.antigravity.image.collect`. It is forced by the merge rules — a list replaces and is never appended to, so a host that adds `--settings /home/runner/.claude/capitoline.json` has to write the whole command line out — and it leaves open exactly the drift the overlay exists to close: after a pull that adds a flag to `claude`'s args the host keeps passing the old list, `npm run check-config` stays green because the schema is satisfied either way, and nothing reports it. Mitigated for now by a re-read command in `docs/deploy.md` §7, which is a step in a runbook and therefore only as reliable as whoever runs it. The way out is to stop duplicating: a dedicated key the host sets instead of the whole list (`args_extra`, or a `settings_file` the claude adapter appends as `--settings <path>` when set), or a `check-config` that fails when the overlay's list does not start with the repository's. The first removes the problem, the second only reports it.

## Providers

- **A busy provider is not an exhausted one.** During the first real council deliberation (2026-09-22) Antigravity answered `agy-gpt-oss` with `UNAVAILABLE (code 503): No capacity available for model gpt-oss-120b-medium on the server` and the prose "Our servers are experiencing high traffic right now, please try again in a minute". `classifyError` called it `rate_limited`, because the `RATE` pattern lists `capacity` for the exhaustion messages and "No capacity available" contains the word. Three wrong consequences followed: the whole Antigravity provider was paused for a minute while its other seat was answering fine; the strike counter advanced, which doubles the wait on the next occurrence, over a condition that clears itself in seconds; and the council lost a ranking. The five error kinds have no name for a transient failure of the provider's own infrastructure, which is what this is. Fix: add a sixth kind — `busy` — classified from `\b503\b`, `UNAVAILABLE`, `no capacity`, `high traffic`, `try again`, retried after a few seconds by the caller, never pausing the provider and never counting as a strike; and keep `capacity` out of the `RATE` pattern once the new kind owns it. The council should retry a `busy` member in place rather than stepping down its chain: the model is not refused, the server is full. This is the mirror image of the Fable finding (`docs/spike-2026-09.md` §9): there a real refusal was not recognised because its prose says nothing about quotas, here a transient fault was taken for one. Both say the same thing — classify from a structured code where one exists, and treat prose as the last resort.


- A decisive capture for Codex's cached input. The one taken on the host (2026-09-22, the same prompt twice through `codex exec`) gave `input=13399 cached=4480` then `input=11738 cached=2432`: the input moves between identical prompts, so the numbers alone exclude neither reading. What it would take is a prompt whose input token count is stable across runs — no session history, no repository context, nothing dated injected by the CLI — sent twice, the second run hitting the cache: only then does `cached` counted inside or beside `input` show up as a difference in the total. ## Phase 2 and beyond

- **Cloudflare MCP Server Portals (beta)**: register `/mcp` in a portal (Zero Trust → Access controls → MCP Portals) to get OAuth login, per-tool policies and invocation logs instead of the raw service token in Claude Code's config. To verify: whether the portal forwards progress notifications (the council needs them) and how it coexists with the Access service-token policy already on the hostname (a second hostname for the portal may be needed).


**OpenAI-compatible API adapter.** For self-hosted inference only — a company inference platform, Ollama, vLLM. No pay-per-use public APIs, by the owner's rule. This adapter also enables a stateless Kubernetes/NKP deployment and lets a company inference platform register Capitoline as a backend (Agent Gateway / Unified Endpoints) and as an MCP server (the platform 2.8).

**What the first council still leaves for later.** Of the three candidates recorded here, two shipped on 2026-09-22 (see Shipped): `capitoline-fast`, the panel without the ranking stage, and — not foreseen when this was written — `capitoline-gemini`, the first capability ladder. What is left is the revision round, where a member sees the panel's verdict on its own answer and rewrites it, and the chain of roles below. What both still need is the measurement: the deliberation already reports every ranking and the aggregate, so agreement *between families* — how often the Anthropic seat and the OpenAI seat rank the same answer first, and whether the two seats on one subscription agree more than the rest — is computable from the rows already stored, as the site's own council does it. Until that number exists there is nothing to say which variant is better, only which is cheaper. `capitoline-fast` is what makes it answerable at last: the same question through both shapes is what says whether the four ranking calls buy anything.

**The other two capability ladders.** `capitoline-claude` and `capitoline-openai`, each one family at three rungs, are two configuration blocks and no code — the same shape as `capitoline-gemini`, with that provider's `concurrency` raised to three and three model entries whose `cli_model` carries the reasoning level. They wait on the first ladder's results: if the three Gemini rungs agree over a sample of real questions, the instrument is measuring something and the other two are worth their calls; if they disagree at random, one ladder is enough and the other two would only spend windows. The Claude ladder is also the expensive one — three calls into the weekly window that is already the scarce one — which is exactly why it is not the one that went first.

**Council variant: a chain of roles, not a panel.** A second strategy, under its own model name (`capitoline-critique` or similar), where the members do different jobs instead of the same one: one drafts, one attacks the draft, one rewrites from both. It answers a different question than the panel does — "how do I improve this answer" rather than "which answer is best" — and it deliberately gives up the anonymous ranking, which only works while the members are symmetric and their answers comparable. Worth measuring against the panel on the same prompts before deciding which one becomes the default; the panel ships first because the ranking is the part with published calibration behind it. Roles stay decoupled from models, as the member list already is. This is also the variant that would finally justify a strategy object in the code: `capitoline-fast` needed one prompt to differ and one stage to be skipped, which a `ranking` boolean covers, while a chain of roles is three different prompts in a different order — a second strategy is what an abstraction for strategies has to pay for (spec §12.9).

**Antigravity text rate limits.** The same "reports success but the error is in the text" pattern, now confirmed and handled for image generation, may also occur for text output — verify this and, if confirmed, call `detectQuotaExhausted` (`src/providers/errors.ts`, already written for the image path) from the text path of `CliProvider.execute()` too.

**Real error fixtures.** Capture real fixtures (expired token, exhausted window) for all three CLIs, recorded when the conditions actually occur rather than synthesized. One is now in: `test/fixtures/antigravity/image-429.jsonl`, the image quota refusal captured on 2026-09-21. Still synthetic: every expired-token case, and the text-side window for all three. Derived rather than synthetic, and named here so nobody reads them as captures: the council's stage recordings (`council-ranking.jsonl` under all three providers, `council-synthesis.jsonl` under `claude`) are the chat recordings with the answer text swapped and nothing else, so the envelope each adapter parses is still the one the real CLI produced — only the words in it were never said.

**Attachments over MCP.** The `ask_model` tool takes a prompt and nothing else, so an image can be sent to a model through `POST /v1/chat/completions` (data-URL content parts, `InternalRequest.attachments`) but not through MCP. **Deliberately deferred in B5, 2026-09-22**, as that task's own text recommends: the council of phase 2 deliberates on text, no caller has asked for it, and adding it is not one parameter but a decision about how bytes travel over JSON-RPC — base64 inside a tool argument, counted against the client's own context and repeated in every retry, against a file path the gateway would have to be allowed to read from the client's machine, which it is not. Revisit when a caller needs it, and take the HTTP path as the shape to mirror.

**Two-container pod shape.** Gateway and runner as separate containers in one pod, communicating over a local socket, as the clean alternative to running sudo inside a single container.

## Shipped

**Antigravity image generation — done (2026-09-21).** `POST /v1/images/generations` and the MCP tool `generate_image`, served by models declared `kind: image`. The silent 429 (the run reports SUCCESS and hides the refusal in a tool step) is detected from the tool event's raw JSON by `detectQuotaExhausted`, and the absolute reset instant the provider returns becomes the provider pause — never an assumed five hours, because the longer of the two windows resets in days. The image itself never reaches the sandbox: it is collected out of the CLI's own home by `scripts/capitoline-collect-image` through sudo and gated on `image.min_bytes` as a second line of defence against a truncated or placeholder file. Findings in `docs/spike-2026-09.md` §8, install steps in `docs/deploy.md` §7.1, both fixtures real. Left as it is by design: `size` is accepted and ignored, since the CLI's tool has no size parameter. Image quota state done (2026-09-21): `UsageStore.imageWindow` counts the successful generations of the 5-hour window, `image.quota_per_window` supplies the limit, and `/health` exposes `imageQuota` (`/v1/models` shows `used` and `limit` for the image models still available). Only the short window is countable locally, and only as a lower bound; the longer one stays known only from the reset instant a refusal carries, reported by `/health` and by the MCP `list_models` tool.

**The council — done (2026-09-22).** `capitoline`, a virtual model asked for in `model` like any other and served by the same HTTP and MCP surfaces (`ask_council`): four seats of different families answer the question independently, rank each other's answers without knowing who wrote what, and a judge seated apart synthesizes — nine calls in three stages, every one of them through `Core.execute()`, so the queue, the pauses, the health state and the usage rows apply to a member exactly as to a request a client made directly, and the council never talks to a provider. The three prompts are the strategy and live in `src/council/prompts.ts` under a `STRATEGY_VERSION`: changing them changes the model's name, not the behaviour of a name already measured. Design in the spec §12, use in the README, cost and configuration in `docs/deploy.md` §7 and §9.

The two open judge questions are closed, each as an option with an opinionated default:

- `judge_allow_member` (default `false`): the judge is a seat of its own, and `claude-haiku` closes its chain precisely because it sits in no seat — with the default, a day when Fable and Opus are both refused would otherwise leave the judge nothing after eight of the nine calls. It costs one call in nine and removes any question of a synthesizer weighing an answer it wrote itself; `true` reproduces karpathy/llm-council's shape.
- `judge_blind` (default `true`): the judge is given the labelled answers and the aggregate, never the identities, so the deliberation is blind end to end. The transparency moves to the report — the response's `capitoline.council` field carries the un-blinded record, labels beside real model names — rather than being given up.

One thing stayed unconfigurable, as decided: the anonymity of the peer-ranking stage itself, which is the mechanism the whole design rests on, and an option to disable it would only offer a way to produce a skewed ranking without noticing.

Shipped with them, and closing the two entries that asked for them: a seat is a family and an ordered chain walked against the health and quota state, with one step down after an unforeseen refusal, so the Fable refusal of 2026-09-21 costs a fallback and not a deliberation; and `agy-gpt-oss` (`gpt-oss-120b` on Antigravity, one line of configuration) is the open-weights seat, which is what gives the panel a fourth family without any local compute.

**A pause belongs to the model that was refused — done (2026-09-22).** The model pause was keyed by the gateway name, so a refusal on `agy-gemini-pro` left `agy-gemini-pro-high` to rediscover the same exhausted model by spending a call, although the two are one id: `gemini-3.1-pro-high`. It is now keyed by the provider and **the id the CLI was actually given** — which is not `cli_model` either, because `effort_suffix` puts the level inside the id, so the same request at `low` is a different model to the provider and rightly a different pause. One resolver (`cliId`, `src/providers/adapter.ts`) answers for the command line, for the pause and for `/v1/models`, so the id refused and the id recorded cannot drift apart; `Provider.cliId()` exposes it to `Core`, and `HealthStatus.cliId` carries it out of a probe, which picks its own effort and is the one caller whose id nothing outside could derive. The provider is part of the key because two subscriptions serve ids of the same name (`claude-sonnet-4-6` is Anthropic's and Antigravity's). Restored rows are validated against the ids the configuration can actually reach, so a row an older build wrote under a gateway name is dropped rather than restored under a key nothing looks up. This was the prerequisite for exposing every model: each new fixed name is by construction an alias of an id another entry already reaches.

**Token accounting said rather than forced — done (2026-09-22).** Each of the three adapters follows the convention of the CLI it reads, and each is right for it: `codex.ts` adds neither `cached_input_tokens` nor `reasoning_output_tokens` because OpenAI reports both inside the prompt and completion counts, `claude.ts` adds the cached reads because Anthropic reports them beside the input, `antigravity.ts` adds its cached reads and not its thinking tokens because that CLI leaves the first out of its total and keeps the second inside the output (measured, `docs/spike-2026-09.md` §10). The consequence — a token count means something different from one provider to the next, and a per-caller sum in `GET /v1/usage` mixes the three conventions — is now said where the numbers are read (`docs/deploy.md` §9, `README.md`) and pinned by `test/docs.test.ts`, instead of being hidden under one formula imposed on three conventions. What is left open is only the empirical check, above.

**The council variants — done (2026-09-22).** Two more councils beside the reference panel, both asked for the same way and both in `/v1/models`. `capitoline-fast`: the four default families and the same judge with `ranking: false`, so stage 2 never runs — five calls instead of nine, the judge synthesizing with no aggregate to weigh, and the shape recorded in the response so an empty ranking is never read as one that failed. `capitoline-gemini`: the first capability ladder, `gemini-3.1-pro-high`, `gemini-3.8-flash-high` and `gemini-3.8-flash-low` seated as three rungs of one family, ranking each other blind and judged from outside by `claude-haiku`, with `agy-claude-sonnet` behind it so an unforeseen refusal does not throw away the six Gemini calls already spent and the step down spends no Anthropic window, with `min_members: 3` so a ladder missing a rung refuses rather than measures nothing. The ladder is configuration only; the fast shape cost one flag in `CouncilSchema`, one branch in `deliberate()` and one paragraph in `synthesisPrompt`, and deliberately no strategy object. The concurrency rule stayed **per council**, measured against the largest council each provider is seated in, so the ladder's three Antigravity rungs are the whole of `providers.antigravity.concurrency: 3` and no other provider moved. Two variants were rejected and their reasons are in spec §12.9 so nobody proposes them again: a two-seat council keeping the ranking (two members cannot break a tie) and a panel leaving Anthropic out to spare its quota (the seat already degrades by itself). The judge options this list asked for were closed with the first council, above, and both councils take them as they are. What is still owed is the measurement — one real deliberation through each shape, its cost in calls and tokens recorded in `docs/spike-2026-09.md`.
