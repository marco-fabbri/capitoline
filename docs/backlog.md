## Tests

## Council

- **A judge that crashes does not step down its chain.** Seen on 2026-09-29 (`docs/measurements/2026-09-29-grok-seat/README.md`, run conditions): with `claude-fable` out, `antigravity-claude-opus` judged, `agy` failed once to recognise its own model id, and the deliberation ended with no synthesis after eight calls — the same model answered normally minutes later. `STEP_DOWN` holds only `rate_limited` and `auth_expired`, on the reasoning that a crash, a timeout or unreadable output "would repeat themselves". For a seat that is right; for the judge it is expensive, since eight calls are already spent and the next model of the judge chain is usually on another provider, where a CLI crash does not repeat. Proposal: let the judge, and only the judge, step down once on `cli_crashed` and `bad_output` when it has not yet written a word (the existing `!spoken` guard) and the next model is on a different provider. Needs a test and a spec §12.2 line; not urgent — one occurrence in thirty days of logs.

## Providers

- **Antigravity text can arrive twice.** Found 2026-09-29 by scanning the 181 member answers and rankings kept in `docs/measurements/`: two texts, both from `antigravity-gpt-oss`, hold a truncated beginning followed by the whole text started again — `2026-09-23-council/results-panels/capitoline__rf3-min-nodes.json` (an answer cut at "| **Node count**", then "**Answer**…" from the top) and a ranking in the 2026-09-29 Grok-seat run, whose raw results are not published (cut at "break", then the full JSON array, which `parseRanking` rejected as "not JSON", so the vote was lost). A client would receive the same spliced text. `parse()` in `src/providers/antigravity.ts` appends every `agent_response` `text_delta` whatever its `step_index`, so a CLI that restarts its response step — a retry after a stream error, presumably — is concatenated. Not yet understood, so no code before evidence: first log the `step_index` of `agent_response` steps when a text run has more than one, and keep the raw stream as a fixture when it recurs. Then the fix: for a non-streamed call keep only the last response step's text; for a streamed call the first part has already reached the client, so end the stream with an error rather than serve a spliced answer.

- **Grok Build as a fourth provider — measured and declined (2026-09-29).** The spike (`docs/spike-2026-09.md` §12) found the CLI workable: the subscription signs in on the headless host with `grok login --device-auth`, `-p … --output-format json|streaming-json` gives the text, token usage and the real model id, and `--deny` rules for every tool family are the only lockdown that holds (`--tools`, `--disallowed-tools` and `dontAsk` did not stop the tools). ## Server

- **An optional dashboard and management UI.** Everything the gateway knows is already answerable over HTTP — `/health` (providers, pauses, image quotas, models and why one is unavailable), `/v1/models`, `/v1/usage` (callers over a day, real model identities over a week), the usage table itself — but reading it means `curl` and `jq`, and the owner would like a page. Optional by construction: a static single-page UI served by the same process under `/ui`, off by default (`server.ui.enabled: false`), and reading only the JSON the API already serves, so it adds no second source of truth and no build step worth the name (one HTML file, no framework). Two ways to reach it, matching the two identities above: behind Cloudflare Access through the tunnel, where the browser login policy the owner already has is the whole of the authentication; or exposed directly, where it signs in with a key the gateway issued (shipped 2026-09-27) kept in the browser's session and sent as `Authorization: Bearer`. What it shows: the health page, the models with their availability, pauses and quotas, usage per caller and per model with the tokens, and the last deliberations by id with their calls. What it manages, deliberately little at first: nothing that lives in the configuration file, which stays the source of truth (design §8.5) — so no editing of models, seats or keys from the page — but the two things an operator does at 3 a.m. with `sqlite3` today: clearing a pause by hand, and naming a caller. Anything more is a second application, not a page. Recorded 2026-09-27 at the owner's request, as its own item.

- **The health-check interval, configurable.** Every provider is probed with one real call an hour (`src/main.ts`, `startHealthLoop(60 * 60 * 1000)`), 24 calls a day each, whatever the subscription. On the owner's plans that is noise; on a free tier — Codex Free is a few dozen messages per 5 hours, Antigravity's free plan a weekly quota with no published figure (checked 2026-09-28) — it is a real share of the allowance spent on knowing the service is alive. `server.health_interval_s` in the configuration, default the current hour, `0` for "at startup only", and the runbook saying when a longer interval is worth it. Small. Recorded 2026-09-28.

## Phase 2 and beyond

- **Server-side conversation state (the Responses API) — not built, on purpose (2026-09-29).** Chat Completions is stateless: the client resends the whole `messages` history every turn, which is what every client in use does, and the gateway already renders that history into one prompt (`flatten`, `src/core/prompt.ts`). The Responses API adds state on the server (`previous_response_id`, conversation objects); the design spec left `/v1/responses` out of scope. Not built because nothing needs it and because it would make the gateway store conversation text on disk for the first time — today `usage.sqlite` holds calls, windows, pauses, keys and caller names, never a prompt. Reopen when a client worth serving speaks only the Responses API. The design, decided now so that day starts from it: state lives in the gateway, never in the CLI — each turn's input and output text stored by response id and replayed through the same stateless path, so the runner keeps its empty directory and disabled sessions (`claude --resume` and `codex exec resume` rejected for that reason); a response id usable only by the caller that created it (404 otherwise); `store: false` honoured by writing nothing; a TTL (30 days, say) pruned like the pauses, and a size cap per conversation; its own database file, apart from `usage.sqlite`, so usage can be kept and shared without conversation text; councils and image models stay stateless.

- **Cloudflare MCP Server Portals (beta)**: register `/mcp` in a portal (Zero Trust → Access controls → MCP Portals) to get OAuth login, per-tool policies and invocation logs instead of the raw service token in Claude Code's config. To verify: whether the portal forwards progress notifications (the council needs them) and how it coexists with the Access service-token policy already on the hostname (a second hostname for the portal may be needed). **Open, to be reasoned about (2026-09-28): Capitoline as a claude.ai web connector.** A custom connector is called from Anthropic's servers (`160.79.104.0/21`), not from the browser, so it stops at Access: claude.ai cannot send the service-token headers. Its authentication options (claude.com/docs/connectors/building/authentication): OAuth with DCR or CIMD by default; static request headers in beta, for a limited set of organizations and standard header names only (`authorization`, `x-api-key`, `x-auth-token`); none. Two ways, not chosen yet: a static `Authorization: Bearer cap_…` — the gateway's own key, a standard name — with an Access Bypass for Anthropic's range on `/mcp`, the key remaining the real guard (needs the owner's account to show the beta "Request headers" section); or OAuth through Access, which is this item. Either way unverified: how long claude.ai waits for a tool (a council takes minutes) and whether it honours progress notifications.


**What the first council still leaves for later.** Of the three candidates recorded here, two shipped on 2026-09-22 (see Shipped): `capitoline-fast`, the panel without the ranking stage, and — not foreseen when this was written — `capitoline-gemini`, the first capability ladder (since moved out of the shipped file into `docs/measure-a-model.md`). What is left is the revision round, where a member sees the panel's verdict on its own answer and rewrites it, and the chain of roles below. What both still need is the measurement: the deliberation already reports every ranking and the aggregate, so agreement *between families* — how often the Anthropic seat and the OpenAI seat rank the same answer first, and whether the two seats on one subscription agree more than the rest — is computable from the rows already stored, as the site's own council does it. Until that number exists there is nothing to say which variant is better, only which is cheaper. `capitoline-fast` is what makes it answerable at last: the same question through both shapes is what says whether the four ranking calls buy anything.

**Council variant: a chain of roles, not a panel.** A second strategy, under its own model name (`capitoline-critique` or similar), where the members do different jobs instead of the same one: one drafts, one attacks the draft, one rewrites from both. It answers a different question than the panel does — "how do I improve this answer" rather than "which answer is best" — and it deliberately gives up the anonymous ranking, which only works while the members are symmetric and their answers comparable. Worth measuring against the panel on the same prompts before deciding which one becomes the default; the panel ships first because the ranking is the part with published calibration behind it. Roles stay decoupled from models, as the member list already is. This is also the variant that would finally justify a strategy object in the code: `capitoline-fast` needed one prompt to differ and one stage to be skipped, which a `ranking` boolean covers, while a chain of roles is three different prompts in a different order — a second strategy is what an abstraction for strategies has to pay for (spec §12.9).

**Antigravity text rate limits.** The same "reports success but the error is in the text" pattern, now confirmed and handled for image generation, may also occur for text output — verify this and, if confirmed, call `detectQuotaExhausted` (`src/providers/errors.ts`, already written for the image path) from the text path of `CliProvider.execute()` too.

**Real error fixtures.** Capture real fixtures (expired token, exhausted window) for all three CLIs, recorded when the conditions actually occur rather than synthesized. One is now in: `test/fixtures/antigravity/image-429.jsonl`, the image quota refusal captured on 2026-09-21. Still synthetic: every expired-token case, and the text-side window for all three. Derived rather than synthetic, and named here so nobody reads them as captures: the council's stage recordings (`council-ranking.jsonl` under all three providers, `council-synthesis.jsonl` under `claude`) are the chat recordings with the answer text swapped and nothing else, so the envelope each adapter parses is still the one the real CLI produced — only the words in it were never said.

**Attachments over MCP.** The `ask_model` tool takes a prompt and nothing else, so an image can be sent to a model through `POST /v1/chat/completions` (data-URL content parts, `InternalRequest.attachments`) but not through MCP. **Deliberately deferred in B5, 2026-09-22**, as that task's own text recommends: the council of phase 2 deliberates on text, no caller has asked for it, and adding it is not one parameter but a decision about how bytes travel over JSON-RPC — base64 inside a tool argument, counted against the client's own context and repeated in every retry, against a file path the gateway would have to be allowed to read from the client's machine, which it is not. Revisit when a caller needs it, and take the HTTP path as the shape to mirror.

**Two-container pod shape.** Gateway and runner as separate containers in one pod, communicating over a local socket, as the clean alternative to running sudo inside a single container.

**A busy provider is not an exhausted one — done (2026-09-22).** A sixth `ErrorKind`, `busy`, for a transient failure of the provider's own infrastructure. `capacity` has left the rate-limit pattern, which is why the captured `UNAVAILABLE (code 503): No capacity available for model gpt-oss-120b-medium` read as an exhausted subscription and paused the whole of Antigravity for a minute while its other seat answered. The classifier tries `busy` **before** `rate_limited`: "please try again in a minute" sits beside a quota reset in more than one CLI's prose, and a 503 that also says "rate limit" is still a 503 — the structured status is the fact, the prose the last resort (spike §9). `Core` does nothing with it: no pause, no strike, which is what the kind is for. Over HTTP it is a 503 with `Retry-After: 5`, not the minute a rate limit gets, because the condition clears by itself. The council keeps it **out of** `STEP_DOWN` and waits five seconds to ask the same model again, once: the model was not refused, so the chain's next model — often on the same provider — buys nothing, and the seat keeps its step down for a real refusal.

**Host sizing, and ladders as a recipe — done (2026-09-23).** Concurrency was a guess shaped by quota worries — Claude 2, Codex 1, Antigravity 3 — and the spec's "2 vCPU, 4 GB" had no arithmetic behind it. `scripts/measure-cli-resources.py` now measures what one run costs by summing each run's process tree (which is how Codex's Node wrapper, ~36 MB around a ~78 MB native binary, stopped being an unexplained process): `claude` ~210 MB, `codex` ~115 MB (147 generating an image), `agy` ~240 MB, the idle host ~140 MB, CPU a hundredth to a tenth of a core over a run's life. Design §4.1 holds the table and the formula, `config/capitoline.yaml` holds each CLI's `memory_mb` next to `concurrency: 10` for all three, and the gateway checks the sum against its real memory limit at startup and warns when it does not fit (`src/sizing.ts`). Ten per CLI needed about 6.7 GB on those figures (7.2 GB after the load measurement of the 27th), so the host wants 8 GB. In the same change the capability ladder left the shipped file: listed in `/v1/models` beside the panels it read as a council to use, and it is an instrument. `docs/measure-a-model.md` carries it instead, for Gemini, Claude and Codex alike, to add to an overlay for as long as a measurement runs; the test suite loads all three over the shipped file and runs the Gemini one end to end.

**The flaky test — done (2026-09-23), and it was Tailscale.** A test failed about once in twenty or thirty full runs, under a different name each time, never with its file alone. Two explanations were written down and both were wrong: a queue budget (it recurred in a test with no queue), then keep-alive connection reuse (ruled out by `superagent`'s own default, `agent: false`, which never pools). The fix came from evidence instead. A setup file now records every HTTP parse error with the bytes Node attaches to it, and every server a test starts with its address and port (`test/setup/http-diagnostics.ts`); the suite was then run in a loop. **Reproduced at run 20**: a test got `401` although its app has no access control. Its server was on port 49557, held by no other test process, and a request to `127.0.0.1:49557` from outside the suite answered `401 auth required` with a `Tailscale-Version` header — Tailscale's local API on the owner's Mac.

`supertest` starts each app with `app.listen(0)` and no host, binding every interface, then connects to `127.0.0.1`. macOS lets that bind take a port another program holds on `127.0.0.1` alone, and the connection goes to the more specific listener. When the random port coincided with Tailscale's, or with a local service that does not speak HTTP (the parse error caught the day before), the test talked to the wrong program. The fix binds every test server to loopback, where such a port cannot be handed out: `supertest` through the setup file, which fixes the request URL once the server is listening, and the five tests that start a real server explicitly. **Verified with 100 consecutive full-suite runs, all green**, five times the run count it took to reproduce, and `test/server.test.ts` alone 20 times out of 20. The gateway itself was never affected: it binds `127.0.0.1` explicitly. The recording stays, so the next intermittent network failure arrives with its evidence.

**A model that tries a tool answers nothing — done (2026-09-23).** Found by the council measurement: asked something they could check on a machine, `gemini-3.1-pro-high` and `gemini-3.8-flash-high` called `run_command`, the runner's `strict` permission soft-denied it — confirmed on the host that nothing ran — and Antigravity 1.2.8 ended the run with an empty response. The ladder lost its two best rungs on two questions of six, and a direct request answered `200` with empty content. Two fixes. A text run that ends with no text is now `bad_output` in the provider layer, once, so the council and a direct request agree, and the error carries what the run spent. And `system_preamble`, a standing instruction on every Antigravity text run: no tools, answer from what you know, say what you are unsure of instead of checking it — the last clause being the behaviour the model uses in place of the one that fails. The two questions were run again and every rung answered (`docs/measurements/2026-09-23-council/`).

**A stray empty database, and the line that would have named it — done (2026-09-23).** `/var/lib/capitoline/capitoline.sqlite`, zero bytes, created by something run in that directory without the overlay: `usage.db_path` is the relative `capitoline.sqlite` in the repository and the absolute `/var/lib/capitoline/usage.sqlite` in the host's overlay. Harmless as it stood, and not harmless if the service had ever started without the overlay — usage would have landed in the empty file, the history would have split in silence and `/v1/usage` would have reported an empty day with nothing saying why. Removed. Logging the resolved path at startup was the obvious second half and was **not** added: the startup line prints which files were loaded and never what is in them, which is a stated decision with a test behind it, and the signal is already there without printing a value — `overlayKeys` carries `usage.db_path` exactly when the overlay set it, so a service started without the overlay says so by that key's absence, and that absence is the only way the history could split. Refusing a relative `db_path` outright was the other option and the wrong one: it is the sensible default for a developer running from the clone.

**The overlay stopped copying the command line — done (2026-09-23).** `providers.claude.args` was written out in full in the overlay to append two items to it, because `mergeConfig` replaces a list and never appends. **Which model actually answered — done (2026-09-23).** The configuration names CLI aliases rather than dated ids, and that is right: the day Anthropic pointed `opus` at Opus 5.5 the gateway served it with nothing changed. What was missing is any record of *when* that happened, so every measurement the project had taken was undated underneath — `claude-opus` in the usage table and in `docs/spike-2026-09.md` §11, and no way to tell whether a number that moved meant the council changed or the model did.

The bullet asked for all three providers; the answer is one. **Only Claude's names are aliases.** `gpt-6-astra` and `gemini-3.8-flash-high` are the models themselves, named outright in the configuration, so a column they filled would say "unchanged, as always" on every row. They report nothing and `cli_model_id` is null for them, which is the honest value and the same choice `caller` made.

The id comes from `message_start.message.model` in the stream the adapter already parses, not from the `result` object's `modelUsage` keys: both carry it, and `modelUsage` is `{}` in every error capture while `message_start` arrives before anything can go wrong. Confirmed against a real run on the host before the code was written. The column was added with the pattern the store has used three times (`PRAGMA table_info` then a guarded `ALTER TABLE`, before the statements are compiled), so a deployed database keeps its history. `GET /v1/usage` now answers `.models` beside `.callers`: which real model served each gateway name over the last week, a week and not a day because the reading is the change.

**A pause belongs to the model that was refused — done (2026-09-22).** The model pause was keyed by the gateway name, so a refusal on `antigravity-gemini-pro` left `antigravity-gemini-pro-high` to rediscover the same exhausted model by spending a call, although the two are one id: `gemini-3.1-pro-high`. It is now keyed by the provider and **the id the CLI was actually given** — which is not `cli_model` either, because `effort_suffix` puts the level inside the id, so the same request at `low` is a different model to the provider and rightly a different pause. One resolver (`cliId`, `src/providers/adapter.ts`) answers for the command line, for the pause and for `/v1/models`, so the id refused and the id recorded cannot drift apart; `Provider.cliId()` exposes it to `Core`, and `HealthStatus.cliId` carries it out of a probe, which picks its own effort and is the one caller whose id nothing outside could derive. The provider is part of the key because two subscriptions serve ids of the same name (`claude-sonnet-4-6` is Anthropic's and Antigravity's). Restored rows are validated against the ids the configuration can actually reach, so a row an older build wrote under a gateway name is dropped rather than restored under a key nothing looks up. This was the prerequisite for exposing every model: each new fixed name is by construction an alias of an id another entry already reaches.

**Token accounting said rather than forced — done (2026-09-22).** Each of the three adapters follows the convention of the CLI it reads, and each is right for it: `codex.ts` adds neither `cached_input_tokens` nor `reasoning_output_tokens` because OpenAI reports both inside the prompt and completion counts, `claude.ts` adds the cached reads because Anthropic reports them beside the input, `antigravity.ts` adds its cached reads and not its thinking tokens because that CLI leaves the first out of its total and keeps the second inside the output (measured, `docs/spike-2026-09.md` §10). The consequence — a token count means something different from one provider to the next, and a per-caller sum in `GET /v1/usage` mixes the three conventions — is now said where the numbers are read (`docs/deploy.md` §9, `README.md`) and pinned by `test/docs.test.ts`, instead of being hidden under one formula imposed on three conventions. The empirical check it left open was run on 2026-09-23 and settled it for Codex: the cached tokens are inside `input_tokens`, measured with an input count that held at 14 387 across three runs while the cached count went from 0 to 13 824 (`docs/spike-2026-09.md` §10). Nothing changed in `codex.ts`, because it was already right.
