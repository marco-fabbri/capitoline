## Tests

- **A flaky test in the suite, still unreproduced — and the first diagnosis was wrong.** Seen four times: three on 2026-09-22 and once on the 23rd, each a single failure that passed on the next run with nothing changed, each under a different name — `POST /v1/images/generations > maps provider error timeout to 504` the first time it was named, `access middleware placement > protects /v1 and /mcp before the body is parsed, leaves /health open` the last.

  The fix of the 22nd removed a hundred-millisecond queue budget from `test/server.test.ts` and claimed the class of failure was gone. The failure of the 23rd came afterwards, in a test with no queue in it at all — pure supertest against the app, a 401 or a 200 — so that diagnosis was at best incomplete and should not have been stated as a result.

  The better hypothesis explains what the first one could not, which is **why the name keeps changing**. Four tests in that file start a real server with `app.listen(0)`, abort a stream in the middle and close the server; work a provider generator still has in flight when its socket goes can outlive the test, and an error it raises lands in whichever test happens to be running. Every failing test named so far comes after the first of those four. Not confirmed: the one piece of evidence that would settle it, the failure's own message, was lost both times it was caught, because only a summary line was read.

  **Caught with its evidence, 2026-09-23**, the first time the saved report was there to read. Test `POST /v1/chat/completions > rejects {"tools":[{}]} with 400`, error `Parse Error: Expected HTTP/, RTSP/ or ICE/` raised in Node's HTTP client (`socketOnData`): the test's socket received bytes that were not an HTTP response. Two things follow. That test runs *before* the four real-server tests in the same file, so the leak hypothesis below does not explain this occurrence. And a parse error, rather than a wrong status or a timeout, points at the connection rather than the test's logic: Node's global HTTP agent keeps connections alive by default since v19, every supertest request binds a fresh ephemeral port and closes it, and a request that reuses a pooled socket for a port that has just been recycled can read what another connection left on it. That is the candidate now — **connection reuse across ephemeral ports** — and it is still not confirmed; the discriminating check is to run the suite with the global agent's keep-alive off and see the failure stop over enough runs to mean something, which at one failure in twenty-odd runs is a long experiment rather than a quick one.

  So this time the evidence is kept rather than the cause guessed at. `vitest.config.ts` now writes a full JSON report of every run to `tmp/vitest-last-run.json`; after the next failure, read it before anything else. An error that is not an assertion — a write after end, an unhandled rejection — confirms the leak and points at the test that leaked; an assertion on a status code says the test itself is racing. Only then fix it.

## Council

- **The judge can introduce an error none of the members made.** *Two of the three remedies have shipped; what is left is the measurement, and the third remedy waits on it.*

  Measured on the first ladder deliberation (2026-09-22, `capitoline-gemini` on a Nutanix RF2 question whose ground truth the owner could verify). The blind peer ranking worked: it put `antigravity-gemini-flash-high` first unanimously, and that answer was also the only one correct on the contested point, saying "zero redundancy on **affected blocks**" where the others claimed both replicas survive. The judge, `claude-haiku`, then merged the answers and shipped the wrong claim — "both replicas survive on the two remaining nodes", false for about two thirds of the extents in a three-node RF2 cluster — plus a right conclusion attached to the wrong mechanism. Nothing in the design can catch this: the ranking judges the members' answers and never the synthesis, so an error born in stage 3 is invisible to stages 1 and 2.

  Shipped since: **a stronger judge**, every chain now opening on the top model of a family rather than the cheapest of one (`config/capitoline.yaml`, same day); and **a judge told not to blend**, `STRATEGY_VERSION` 2, where the synthesis prompt builds on the top-ranked answer, adds from the others only what does not contradict it, and is told outright to assert nothing none of the answers supports and never to merge two contradicting answers into a claim neither made. The ranking stays evidence rather than an order, because the panel's ordering of the tail is noisy (spike §11) and a judge that could not depart from a wrong first place would be a ranking with extra steps.

  And since 2026-09-23, a third remedy nobody had thought of, because it was not a remedy but a bug: **the judge was never the best available**. Every entry of the chain was reachable by a seat, and `judge_allow_member: false` strikes a seated model out, so the judge was whatever the panel had no use for — on a day when `claude-fable` was exhausted, the cheapest entry. The chain is now built around models the seats cannot take, and the paired runs are in `docs/spike-2026-09.md` §11: same question, same day, same seats, judge `codex-gpt-5.6-sol` before and `antigravity-claude-opus` after, with a visibly better synthesis. Two tests pin the property.

  Still open. **The measurement across question shapes**: strategy 2 has three runs now and all on one question, which says the failure did not recur and nothing about whether the prompt helps in general. And then, only if it does not, **the fourth stage**: one member checking the synthesis against the answers, which doubles the tail of every deliberation and should not be built while cheaper remedies are untested.

## Phase 2 and beyond

- **Cloudflare MCP Server Portals (beta)**: register `/mcp` in a portal (Zero Trust → Access controls → MCP Portals) to get OAuth login, per-tool policies and invocation logs instead of the raw service token in Claude Code's config. To verify: whether the portal forwards progress notifications (the council needs them) and how it coexists with the Access service-token policy already on the hostname (a second hostname for the portal may be needed).


**OpenAI-compatible API adapter.** For self-hosted inference only — a company inference platform, Ollama, vLLM. No pay-per-use public APIs, by the owner's rule. This adapter also enables a stateless Kubernetes/NKP deployment and lets a company inference platform register Capitoline as a backend (Agent Gateway / Unified Endpoints) and as an MCP server (the platform 2.8).

**What the first council still leaves for later.** Of the three candidates recorded here, two shipped on 2026-09-22 (see Shipped): `capitoline-fast`, the panel without the ranking stage, and — not foreseen when this was written — `capitoline-gemini`, the first capability ladder. What is left is the revision round, where a member sees the panel's verdict on its own answer and rewrites it, and the chain of roles below. What both still need is the measurement: the deliberation already reports every ranking and the aggregate, so agreement *between families* — how often the Anthropic seat and the OpenAI seat rank the same answer first, and whether the two seats on one subscription agree more than the rest — is computable from the rows already stored, as the site's own council does it. Until that number exists there is nothing to say which variant is better, only which is cheaper. `capitoline-fast` is what makes it answerable at last: the same question through both shapes is what says whether the four ranking calls buy anything.

**The other two capability ladders.** `capitoline-claude` and `capitoline-openai`, each one family at three rungs, are two configuration blocks and no code — the same shape as `capitoline-gemini`, with that provider's `concurrency` raised to three and three model entries whose `cli_model` carries the reasoning level. They waited on the first ladder's results: if the three Gemini rungs agreed over a sample of real questions, the instrument was measuring something and the other two were worth their calls. **That condition is met** (2026-09-23, `docs/measurements/2026-09-23-council/`): over six registered questions of different shapes the blind ranking put the wrong rung last every time one was wrong, and it gave an answer that can be acted on — the middle rung is as correct as the top one, the cheap rung is not. What is left is the owner's decision on cost. `capitoline-openai` would need three concurrent `codex exec` processes on an allowance that becomes Plus in October, which argues for not building it at all; `capitoline-claude` would spend three calls of the Anthropic weekly window per question, which argues for running it only after a reset. The Claude ladder is also the expensive one — three calls into the weekly window that is already the scarce one — which is exactly why it is not the one that went first.

**Council variant: a chain of roles, not a panel.** A second strategy, under its own model name (`capitoline-critique` or similar), where the members do different jobs instead of the same one: one drafts, one attacks the draft, one rewrites from both. It answers a different question than the panel does — "how do I improve this answer" rather than "which answer is best" — and it deliberately gives up the anonymous ranking, which only works while the members are symmetric and their answers comparable. Worth measuring against the panel on the same prompts before deciding which one becomes the default; the panel ships first because the ranking is the part with published calibration behind it. Roles stay decoupled from models, as the member list already is. This is also the variant that would finally justify a strategy object in the code: `capitoline-fast` needed one prompt to differ and one stage to be skipped, which a `ranking` boolean covers, while a chain of roles is three different prompts in a different order — a second strategy is what an abstraction for strategies has to pay for (spec §12.9).

**Antigravity text rate limits.** The same "reports success but the error is in the text" pattern, now confirmed and handled for image generation, may also occur for text output — verify this and, if confirmed, call `detectQuotaExhausted` (`src/providers/errors.ts`, already written for the image path) from the text path of `CliProvider.execute()` too.

**Real error fixtures.** Capture real fixtures (expired token, exhausted window) for all three CLIs, recorded when the conditions actually occur rather than synthesized. One is now in: `test/fixtures/antigravity/image-429.jsonl`, the image quota refusal captured on 2026-09-21. Still synthetic: every expired-token case, and the text-side window for all three. Derived rather than synthetic, and named here so nobody reads them as captures: the council's stage recordings (`council-ranking.jsonl` under all three providers, `council-synthesis.jsonl` under `claude`) are the chat recordings with the answer text swapped and nothing else, so the envelope each adapter parses is still the one the real CLI produced — only the words in it were never said.

**Attachments over MCP.** The `ask_model` tool takes a prompt and nothing else, so an image can be sent to a model through `POST /v1/chat/completions` (data-URL content parts, `InternalRequest.attachments`) but not through MCP. **Deliberately deferred in B5, 2026-09-22**, as that task's own text recommends: the council of phase 2 deliberates on text, no caller has asked for it, and adding it is not one parameter but a decision about how bytes travel over JSON-RPC — base64 inside a tool argument, counted against the client's own context and repeated in every retry, against a file path the gateway would have to be allowed to read from the client's machine, which it is not. Revisit when a caller needs it, and take the HTTP path as the shape to mirror.

**Two-container pod shape.** Gateway and runner as separate containers in one pod, communicating over a local socket, as the clean alternative to running sudo inside a single container.

The silent 429 (the run reports SUCCESS and hides the refusal in a tool step) is detected from the tool event's raw JSON by `detectQuotaExhausted`, and the absolute reset instant the provider returns becomes the provider pause — never an assumed five hours, because the longer of the two windows resets in days. The image itself never reaches the sandbox: it is collected out of the CLI's own home by `scripts/capitoline-collect-image` through sudo and gated on `image.min_bytes` as a second line of defence against a truncated or placeholder file. Findings in `docs/spike-2026-09.md` §8, install steps in `docs/deploy.md` §7.1, both fixtures real. Left as it is by design: `size` is accepted and ignored, since the CLI's tool has no size parameter. Image quota state done (2026-09-21): `UsageStore.imageWindow` counts the successful generations of the 5-hour window, `image.quota_per_window` supplies the limit, and `/health` exposes `imageQuota` (`/v1/models` shows `used` and `limit` for the image models still available). Only the short window is countable locally, and only as a lower bound; the longer one stays known only from the reset instant a refusal carries, reported by `/health` and by the MCP `list_models` tool.

**The council — done (2026-09-22).** `capitoline`, a virtual model asked for in `model` like any other and served by the same HTTP and MCP surfaces (`ask_council`): four seats of different families answer the question independently, rank each other's answers without knowing who wrote what, and a judge seated apart synthesizes — nine calls in three stages, every one of them through `Core.execute()`, so the queue, the pauses, the health state and the usage rows apply to a member exactly as to a request a client made directly, and the council never talks to a provider. The three prompts are the strategy and live in `src/council/prompts.ts` under a `STRATEGY_VERSION`: changing them changes the model's name, not the behaviour of a name already measured. Design in the spec §12, use in the README, cost and configuration in `docs/deploy.md` §7 and §9.

The two open judge questions are closed, each as an option with an opinionated default:

- `judge_allow_member` (default `false`): the judge is a seat of its own, and `claude-haiku` closes its chain precisely because it sits in no seat — with the default, a day when Fable and Opus are both refused would otherwise leave the judge nothing after eight of the nine calls. It costs one call in nine and removes any question of a synthesizer weighing an answer it wrote itself; `true` reproduces karpathy/llm-council's shape.
- `judge_blind` (default `true`): the judge is given the labelled answers and the aggregate, never the identities, so the deliberation is blind end to end. The transparency moves to the report — the response's `capitoline.council` field carries the un-blinded record, labels beside real model names — rather than being given up.

One thing stayed unconfigurable, as decided: the anonymity of the peer-ranking stage itself, which is the mechanism the whole design rests on, and an option to disable it would only offer a way to produce a skewed ranking without noticing.

Shipped with them, and closing the two entries that asked for them: a seat is a family and an ordered chain walked against the health and quota state, with one step down after an unforeseen refusal, so the Fable refusal of 2026-09-21 costs a fallback and not a deliberation; and `antigravity-gpt-oss` (`gpt-oss-120b` on Antigravity, one line of configuration) is the open-weights seat, which is what gives the panel a fourth family without any local compute.

**A busy provider is not an exhausted one — done (2026-09-22).** A sixth `ErrorKind`, `busy`, for a transient failure of the provider's own infrastructure. `capacity` has left the rate-limit pattern, which is why the captured `UNAVAILABLE (code 503): No capacity available for model gpt-oss-120b-medium` read as an exhausted subscription and paused the whole of Antigravity for a minute while its other seat answered. The classifier tries `busy` **before** `rate_limited`: "please try again in a minute" sits beside a quota reset in more than one CLI's prose, and a 503 that also says "rate limit" is still a 503 — the structured status is the fact, the prose the last resort (spike §9). `Core` does nothing with it: no pause, no strike, which is what the kind is for. Over HTTP it is a 503 with `Retry-After: 5`, not the minute a rate limit gets, because the condition clears by itself. The council keeps it **out of** `STEP_DOWN` and waits five seconds to ask the same model again, once: the model was not refused, so the chain's next model — often on the same provider — buys nothing, and the seat keeps its step down for a real refusal.

**A model that tries a tool answers nothing — done (2026-09-23).** Found by the council measurement: asked something they could check on a machine, `gemini-3.1-pro-high` and `gemini-3.8-flash-high` called `run_command`, the runner's `strict` permission soft-denied it — confirmed on the host that nothing ran — and Antigravity 1.2.8 ended the run with an empty response. The ladder lost its two best rungs on two questions of six, and a direct request answered `200` with empty content. Two fixes. A text run that ends with no text is now `bad_output` in the provider layer, once, so the council and a direct request agree, and the error carries what the run spent. And `system_preamble`, a standing instruction on every Antigravity text run: no tools, answer from what you know, say what you are unsure of instead of checking it — the last clause being the behaviour the model uses in place of the one that fails. The two questions were run again and every rung answered (`docs/measurements/2026-09-23-council/`).

**A stray empty database, and the line that would have named it — done (2026-09-23).** `/var/lib/capitoline/capitoline.sqlite`, zero bytes, created by something run in that directory without the overlay: `usage.db_path` is the relative `capitoline.sqlite` in the repository and the absolute `/var/lib/capitoline/usage.sqlite` in the host's overlay. Harmless as it stood, and not harmless if the service had ever started without the overlay — usage would have landed in the empty file, the history would have split in silence and `/v1/usage` would have reported an empty day with nothing saying why. Removed. Logging the resolved path at startup was the obvious second half and was **not** added: the startup line prints which files were loaded and never what is in them, which is a stated decision with a test behind it, and the signal is already there without printing a value — `overlayKeys` carries `usage.db_path` exactly when the overlay set it, so a service started without the overlay says so by that key's absence, and that absence is the only way the history could split. Refusing a relative `db_path` outright was the other option and the wrong one: it is the sensible default for a developer running from the clone.

**A pause belongs to the model that was refused — done (2026-09-22).** The model pause was keyed by the gateway name, so a refusal on `antigravity-gemini-pro` left `antigravity-gemini-pro-high` to rediscover the same exhausted model by spending a call, although the two are one id: `gemini-3.1-pro-high`. It is now keyed by the provider and **the id the CLI was actually given** — which is not `cli_model` either, because `effort_suffix` puts the level inside the id, so the same request at `low` is a different model to the provider and rightly a different pause. One resolver (`cliId`, `src/providers/adapter.ts`) answers for the command line, for the pause and for `/v1/models`, so the id refused and the id recorded cannot drift apart; `Provider.cliId()` exposes it to `Core`, and `HealthStatus.cliId` carries it out of a probe, which picks its own effort and is the one caller whose id nothing outside could derive. The provider is part of the key because two subscriptions serve ids of the same name (`claude-sonnet-4-6` is Anthropic's and Antigravity's). Restored rows are validated against the ids the configuration can actually reach, so a row an older build wrote under a gateway name is dropped rather than restored under a key nothing looks up. This was the prerequisite for exposing every model: each new fixed name is by construction an alias of an id another entry already reaches.

**Token accounting said rather than forced — done (2026-09-22).** Each of the three adapters follows the convention of the CLI it reads, and each is right for it: `codex.ts` adds neither `cached_input_tokens` nor `reasoning_output_tokens` because OpenAI reports both inside the prompt and completion counts, `claude.ts` adds the cached reads because Anthropic reports them beside the input, `antigravity.ts` adds its cached reads and not its thinking tokens because that CLI leaves the first out of its total and keeps the second inside the output (measured, `docs/spike-2026-09.md` §10). The consequence — a token count means something different from one provider to the next, and a per-caller sum in `GET /v1/usage` mixes the three conventions — is now said where the numbers are read (`docs/deploy.md` §9, `README.md`) and pinned by `test/docs.test.ts`, instead of being hidden under one formula imposed on three conventions. The empirical check it left open was run on 2026-09-23 and settled it for Codex: the cached tokens are inside `input_tokens`, measured with an input count that held at 14 387 across three runs while the cached count went from 0 to 13 824 (`docs/spike-2026-09.md` §10). Nothing changed in `codex.ts`, because it was already right.

**The council variants — done (2026-09-22).** Two more councils beside the reference panel, both asked for the same way and both in `/v1/models`. `capitoline-fast`: the four default families and the same judge with `ranking: false`, so stage 2 never runs — five calls instead of nine, the judge synthesizing with no aggregate to weigh, and the shape recorded in the response so an empty ranking is never read as one that failed. `capitoline-gemini`: the first capability ladder, `gemini-3.1-pro-high`, `gemini-3.8-flash-high` and `gemini-3.8-flash-low` seated as three rungs of one family, ranking each other blind and judged from outside, with a chain behind the judge so an unforeseen refusal does not throw away the six Gemini calls already spent (the chain was reopened later the same day, after the first run measured what a cheap judge costs), with `min_members: 3` so a ladder missing a rung refuses rather than measures nothing. The concurrency rule stayed **per council**, measured against the largest council each provider is seated in, so the ladder's three Antigravity rungs are the whole of `providers.antigravity.concurrency: 3` and no other provider moved.
