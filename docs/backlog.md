## Phase 2 and beyond


**What the first council still leaves for later.** Of the three candidates recorded here, two shipped on 2026-09-22 (see Shipped): `capitoline-fast`, the panel without the ranking stage, and — not foreseen when this was written — `capitoline-gemini`, the first capability ladder (since moved out of the shipped file into `docs/measure-a-model.md`). What is left is the revision round, where a member sees the panel's verdict on its own answer and rewrites it, and the chain of roles below. What both still need is the measurement: the deliberation already reports every ranking and the aggregate, so agreement *between families* — how often the Anthropic seat and the OpenAI seat rank the same answer first, and whether the two seats on one subscription agree more than the rest — is computable from the rows already stored, as the site's own council does it. Until that number exists there is nothing to say which variant is better, only which is cheaper. `capitoline-fast` is what makes it answerable at last: the same question through both shapes is what says whether the four ranking calls buy anything.

**Council variant: a chain of roles, not a panel.** A second strategy, under its own model name (`capitoline-critique` or similar), where the members do different jobs instead of the same one: one drafts, one attacks the draft, one rewrites from both. It answers a different question than the panel does — "how do I improve this answer" rather than "which answer is best" — and it deliberately gives up the anonymous ranking, which only works while the members are symmetric and their answers comparable. Worth measuring against the panel on the same prompts before deciding which one becomes the default; the panel ships first because the ranking is the part with published calibration behind it. Roles stay decoupled from models, as the member list already is. This is also the variant that would finally justify a strategy object in the code: `capitoline-fast` needed one prompt to differ and one stage to be skipped, which a `ranking` boolean covers, while a chain of roles is three different prompts in a different order — a second strategy is what an abstraction for strategies has to pay for (spec §12.9).

**Council variant: a debate, in rounds, with a stopping rule.** A third strategy beside the panel and the chain of roles: after the independent answers, each member sees the others' answers, unlabelled as in the ranking, and revises its own, for more than one round, before the judge writes the synthesis. It fits the gateway because everything a council needs is here already: the seats and their fallbacks, the quotas and pauses, the per-deliberation usage rows, the progress stream. Three things decide whether it is worth building, and none is the code:

- **It cannot run "until it is solved".** Nothing in a discussion says a problem is solved. Without an outside check the members converge on each other, not on the truth, and usually within two or three rounds, on a wrong answer as readily as on a right one. So: a maximum of rounds (three, to start from), an early stop when the answers agree, and a ceiling on calls.
- **The cost is not linear.** Every round resends the whole discussion to every member, so tokens grow with the square of the rounds, on subscriptions whose windows a plain panel already spends.
- **It only suits problems that talking can settle.** The CLIs run with their tools off in an empty directory, by design. A design choice, an analysis, a review are in reach; anything that needs running code, tests or a search is an agent's work with tools, outside the gateway, which can still be what that agent asks for a second opinion.

What it would need that does not exist: **deliberations in the background.** A debate lasts tens of minutes, too long for a request held open through a proxy. It starts, returns an id, and its progress and result are read later, from the API or the operator's page.

Measure before building, as for the panel. Since `ask_model` keeps a conversation per model, a client can already run a debate from outside, with one thread per member and no change here. A handful of real problems put through that and through the panel says whether the extra rounds buy anything; only then is it a strategy of the gateway's (`capitoline-debate`).

**Antigravity text rate limits.** The same "reports success but the error is in the text" pattern, now confirmed and handled for image generation, may also occur for text output — verify this and, if confirmed, call `detectQuotaExhausted` (`src/providers/errors.ts`, already written for the image path) from the text path of `CliProvider.execute()` too.

**Real error fixtures.** Capture real fixtures (expired token, exhausted window) for all three CLIs, recorded when the conditions actually occur rather than synthesized. One is now in: `test/fixtures/antigravity/image-429.jsonl`, the image quota refusal captured on 2026-09-21. Still synthetic: every expired-token case, and the text-side window for all three. Derived rather than synthetic, and named here so nobody reads them as captures: the council's stage recordings (`council-ranking.jsonl` under all three providers, `council-synthesis.jsonl` under `claude`) are the chat recordings with the answer text swapped and nothing else, so the envelope each adapter parses is still the one the real CLI produced — only the words in it were never said.

**A container installation: images, and the runner as a service of its own.** Today there is one way to install the gateway: a dedicated Linux machine (a VM or a system container) with systemd and two users, by hand from the runbook or with the Ansible installer. Nothing ships for Docker or Kubernetes, and many who find a project like this expect an image. The gateway itself is easy to package; the CLIs are what makes it a piece of work, for three reasons: each CLI's login is interactive and bound to the machine that did it, so it lives on a persistent volume and is done by hand the first time; the CLIs update often and every update is checked (`docs/update-clis.md`), which an image either rebuilds for or leaves to a volume; and the separation between the gateway and the CLIs rests on `sudo` between two users, which is the unclean part inside one container. In the order it would be built:

1. **The runner as a service.** A small process that owns the CLIs and takes "run this command, with this input, in an empty directory, with this deadline" over a Unix socket, in place of `sudo` from the gateway's process. It is the piece that is actually missing, and it is useful outside containers too.
2. **Two images**, gateway and runner. The gateway's holds no CLI and the runner's holds no key or usage database: the boundary `sudo` draws today becomes the boundary between containers.
3. **An example for each platform**: a compose file for Docker, and for Kubernetes one pod with the two containers and the socket in a shared volume. One pod rather than two: a CLI's capacity is its subscription's, so there is nothing to scale apart; the gateway keeps a single SQLite writer; and the channel between them is "execute this", which inside a pod is a socket nobody else can reach and between pods would be a network service to authenticate and fence. A container per CLI, in the same pod, is the variant for isolating the providers from each other.
4. **The procedures that change**: signing each CLI in inside its container, and updating and checking a CLI there.

Not started, and not needed by an installation on a machine of its own, which stays the supported shape.

**The operator's page, and the routes it stands on — done (2026-10-03).** Recorded here on 2026-09-27 as an optional page under `/ui`, off by default, one HTML file reading the JSON the API already serves. Built that way: `server.ui.enabled` serves three static files (no framework, no build, a content security policy that lets them load only each other), and the page signs in with an administrator's key kept in the browser tab. What it needed and the API did not have became routes under `/v1/admin`, so nothing is the page's alone: usage per day, the latest deliberations, the pauses with a way to lift one or hold a model back by hand, a health or catalog check run now, a test notification, how much each caller has kept (never what), the configuration in force. **Conversations kept by the gateway: the Responses API, and `ask_model`'s `conversation` — done (2026-10-01).** Built to the design recorded here on 2026-09-29, when it was deferred because no client needed it. `POST /v1/responses` serves one model's text answer with OpenAI's shapes (checked against the official SDK, which a test drives: create, continue, stream, retrieve, delete), and `previous_response_id` continues a conversation without resending it. The state lives in the gateway, never in a CLI: each turn's input and output are stored by response id and replayed as text through the same stateless path (`flatten`), so the runner keeps its empty directory and disabled sessions. The store is a database file of its own (`conversations.db_path`), created owner-only, apart from `usage.sqlite` and left out of the backup on purpose. It keeps text only, with a line where an image was. A thread is forgotten 30 days after its last turn (`ttl_days`), and `max_turns` and `max_bytes` cap what a turn replays, since no body limit sees a history the gateway assembles itself. `truncation: auto` drops the oldest turns instead of refusing. A turn is readable only by the caller that created it, and anyone else gets the 404 an unknown id gets. `store: false` keeps nothing, and an abandoned or failed answer leaves nothing. Councils and image models stay stateless. The MCP `ask_model` tool reaches the same store through `conversation` (`"new"`, then the id each answer returns), so a conversation can move between MCP and HTTP under the same key.

**A busy provider is not an exhausted one — done (2026-09-22).** A sixth `ErrorKind`, `busy`, for a transient failure of the provider's own infrastructure. `capacity` has left the rate-limit pattern, which is why the captured `UNAVAILABLE (code 503): No capacity available for model gpt-oss-120b-medium` read as an exhausted subscription and paused the whole of Antigravity for a minute while its other seat answered. The classifier tries `busy` **before** `rate_limited`: "please try again in a minute" sits beside a quota reset in more than one CLI's prose, and a 503 that also says "rate limit" is still a 503 — the structured status is the fact, the prose the last resort (spike §9). `Core` does nothing with it: no pause, no strike, which is what the kind is for. Over HTTP it is a 503 with `Retry-After: 5`, not the minute a rate limit gets, because the condition clears by itself. The council keeps it **out of** `STEP_DOWN` and waits five seconds to ask the same model again, once: the model was not refused, so the chain's next model — often on the same provider — buys nothing, and the seat keeps its step down for a real refusal.

**The flaky test — done (2026-09-23), and it was Tailscale.** A test failed about once in twenty or thirty full runs, under a different name each time, never with its file alone. Two explanations were written down and both were wrong: a queue budget (it recurred in a test with no queue), then keep-alive connection reuse (ruled out by `superagent`'s own default, `agent: false`, which never pools). The fix came from evidence instead. A setup file now records every HTTP parse error with the bytes Node attaches to it, and every server a test starts with its address and port (`test/setup/http-diagnostics.ts`); the suite was then run in a loop. **Reproduced at run 20**: a test got `401` although its app has no access control. Its server was on port 49557, held by no other test process, and a request to `127.0.0.1:49557` from outside the suite answered `401 auth required` with a `Tailscale-Version` header — Tailscale's local API on the owner's Mac.

`supertest` starts each app with `app.listen(0)` and no host, binding every interface, then connects to `127.0.0.1`. macOS lets that bind take a port another program holds on `127.0.0.1` alone, and the connection goes to the more specific listener. When the random port coincided with Tailscale's, or with a local service that does not speak HTTP (the parse error caught the day before), the test talked to the wrong program. The fix binds every test server to loopback, where such a port cannot be handed out: `supertest` through the setup file, which fixes the request URL once the server is listening, and the five tests that start a real server explicitly. **Verified with 100 consecutive full-suite runs, all green**, five times the run count it took to reproduce, and `test/server.test.ts` alone 20 times out of 20. The gateway itself was never affected: it binds `127.0.0.1` explicitly. The recording stays, so the next intermittent network failure arrives with its evidence.
